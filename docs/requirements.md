# RAG型チャットボット 要件定義書

## 1. プロジェクトの背景

製造業の中小企業では、経営判断に必要な情報が公的機関などの公開資料に分散していることがあります。資料の所在を探し、必要な箇所を読み比べて判断材料を整理するには、時間と手間がかかります。

本プロジェクトでは、IPAなどが公開しているPDF資料を対象に、質問に関連する情報を検索し、その情報を根拠として回答するRAG型チャットボットを開発します。RAG（検索拡張生成）は、回答を作る前に関連資料を検索し、その検索結果を参考情報としてLLM（大規模言語モデル）に渡す方式です。

本書は現時点での要件を整理したものです。まだ決まっていない技術や仕様は、決定事項として扱わず「候補」または「要検討」と記載します。

## 2. 解決したい課題

- 必要な公開資料を見つけるまでに時間がかかる。
- PDFの中から質問に関係する記述を探し、読む負担が大きい。
- 複数の資料や年度の違いを見比べ、情報を整理することが難しい。
- AIの回答がどの資料に基づくか分からないと、内容を確認して判断することが難しい。

## 3. システムの目的

1. 登録した公開資料から、利用者の質問に関連する情報を検索する。
2. 検索結果を参考に、質問への回答を生成する。
3. 回答の根拠となった資料名とページ番号を表示し、利用者が原資料を確認できるようにする。
4. 将来的に、複数資料の比較や年度ごとの違いの整理を支援する。

このシステムは経営判断の材料を探して整理するための支援を目的とします。回答を最終判断や専門家の助言に代わるものとして扱うかどうかは、運用ルールと合わせて要検討です。

## 4. 想定ユーザー

- **主な利用者**：従業員約100名の製造業の中小企業における経営者・経営幹部。
- **想定する利用者の知識**：PDFや一般的なWebアプリを利用できることを想定します。RAGやLLMの専門知識は前提としません。
- **運用担当者**：資料の選定、登録、更新、削除などを行う担当者が必要になる可能性があります。担当者の役割や権限の分け方は要検討です。

## 5. 利用シーン

- 経営者が、公開資料に記載された中小企業向けの施策や指針について質問する。
- 経営幹部が、製造業に関係する公開情報を調べ、原資料の該当箇所を確認する。
- 利用者が、回答に付いた資料名とページ番号を手がかりに、原資料の内容を確認する。
- 将来的に、同じテーマを扱う複数資料や異なる年度の資料を比較し、共通点・相違点を把握する。

具体的な質問例、対象業務、利用頻度は要検討です。

## 6. 機能要件

### Phase 1で想定する機能

| ID | 機能 | 要件 |
|---|---|---|
| F-01 | PDF資料の登録 | 選定した公開PDFを検索対象として登録できること。登録方法や利用者の範囲は要検討です。 |
| F-02 | PDFのテキスト抽出 | PDFから検索に利用するテキストを抽出できること。文字情報のないスキャンPDFへの対応方法（OCRなど）は要検討です。 |
| F-03 | チャンク分割 | 抽出したテキストを検索しやすい大きさに分割できること。分割単位や重なり幅は要検討です。 |
| F-04 | 質問入力 | 利用者が自然な文章で質問を入力できること。利用画面や入力制限は要検討です。 |
| F-05 | 関連箇所の検索 | 登録資料から質問に関係する箇所を検索し、回答生成の参考情報として利用できること。検索方式や検索件数は要検討です。 |
| F-06 | 回答生成 | 検索した情報をもとにLLMが回答を生成できること。根拠が不十分な場合の応答方法や回答形式は要検討です。 |
| F-07 | 根拠の表示 | 回答とあわせて、根拠となった資料名とページ番号を表示できること。PDFのページと抽出テキストの対応付け方法は要検討です。 |
| F-08 | 資料の管理 | 登録資料の一覧、更新、削除が必要か、その操作方法を含めて要検討です。 |

### 将来の機能候補

- **Phase 2**：複数資料を対象にした比較、共通点・相違点の整理、年度ごとの差分の説明。
- **Phase 3**：経営課題や業界動向について、公開情報を横断して整理・支援する機能。
- 会話履歴の保存、資料の絞り込み、回答の評価・フィードバックなどは候補ですが、採用するかは要検討です。

## 7. 非機能要件

以下は現時点での目標・検討事項です。具体的な数値や方式は、試作と利用状況を踏まえて決定します。

- **回答の信頼性**：回答が検索結果に基づくようにし、利用者が資料名とページ番号から原資料を確認できること。誤回答や根拠の不一致をどう評価・低減するかは要検討です。
- **使いやすさ**：RAGやLLMに詳しくない経営者・経営幹部にも使い方が分かる画面と説明を目指します。画面仕様は要検討です。
- **性能**：質問から回答表示までの許容時間、同時利用者数、扱う資料数は要検討です。
- **保守性・拡張性**：資料の取り込み、検索、回答生成の責務を分け、将来の比較機能や技術変更に対応しやすい構成を目指します。
- **セキュリティ**：初期段階では社内機密資料を扱わない前提です。アクセス制御、ログの扱い、外部LLMサービスへ送信されるデータの範囲などは、利用するサービスや運用方法に応じて要検討です。
- **可用性・バックアップ**：稼働時間、障害時の対応、データのバックアップと復元方法は要検討です。
- **運用性**：資料の追加・更新・削除、抽出エラーの確認、利用状況の把握方法は要検討です。
- **法令・利用条件への配慮**：各公開資料や利用する外部サービスの利用条件を確認し、保存・処理・表示の方法を決める必要があります。

## 8. 対象データと対象外データ

### 対象データ

- IPAなどの公的機関が公開しているPDF資料を中心とする公開資料。
- 初期段階では、選定した公開PDFを検索・回答生成の対象とします。
- 資料の対象範囲、対象機関、公開資料の取得方法、更新頻度は要検討です。

### 初期段階で対象外とするデータ

- 社内の機密資料。
- 利用許可や利用条件を確認できていない資料。
- PDF以外の形式（Webページ、Word、Excelなど）。将来対応するかは要検討です。
- 画像のみのPDFや、テキスト抽出が困難なPDF。OCRなどで対応するかは要検討です。

## 9. 開発フェーズ

| フェーズ | 内容 | 想定する成果 |
|---|---|---|
| Phase 1 | PDFの情報検索と根拠付き回答 | 公開PDFを対象に質問に関連する情報を検索し、資料名とページ番号を示した回答を返す仕組み。 |
| Phase 2 | 複数資料の比較 | 複数資料の共通点・相違点や、年度ごとの情報の違いを整理する機能。 |
| Phase 3 | 経営・業界情報の整理支援 | 経営課題や業界動向に関する公開情報を整理し、検討を支援する機能。対象テーマと提供範囲は要検討です。 |

各フェーズの完了条件、優先順位、期間は要検討です。後続フェーズの機能は、前フェーズの評価を踏まえて具体化します。

## 10. 技術構成の候補と選定理由

次の構成は候補であり、確定した採用技術ではありません。

| 技術候補 | 想定用途・候補とする理由 | メリット | デメリット・留意点 |
|---|---|---|---|
| Python | PDF処理、検索処理、LLM連携などのアプリケーション開発。データ処理やAI関連のライブラリが豊富なため候補とします。 | 学習資料やライブラリが多く、RAGの各処理を段階的に実装しやすい。 | ライブラリの選定・更新管理が必要。実行環境や依存関係の管理方法も決める必要がある。 |
| Docker | アプリケーションや関連サービスの実行環境を揃える候補です。 | 開発者間や環境間で実行条件を揃えやすく、DBなどのサービスもまとめて起動しやすい。 | Docker自体の学習が必要で、設定やリソース使用量が増える。小規模な試作で必須かは要検討。 |
| PostgreSQL | 資料情報や検索用データを保存するデータベースの候補です。 | 実績のあるオープンソースのリレーショナルデータベースで、構造化データを扱いやすい。 | DBの設計・運用・バックアップが必要。利用規模に対して適切かを検証する必要がある。 |
| pgvector | PostgreSQL上でベクトルを保存し、類似検索を行う拡張機能の候補です。 | データベースを分けずに、資料情報とベクトル検索を扱える可能性がある。 | 拡張機能の導入・設定が必要。検索性能やデータ量との適合性、別の検索方式との比較が必要。 |
| RAG | 検索した資料の情報をLLMに渡して回答を作る方式。回答に資料の根拠を結び付ける目的に合うため候補とします。 | モデルの学習を毎回行わず、登録資料に基づく回答を目指せる。資料を更新して検索対象に反映しやすい。 | 検索漏れや不適切な回答が起きる可能性があり、検索品質・根拠表示・評価方法の設計が必要。 |
| LLM | 検索結果をもとに自然な文章の回答を生成する候補です。 | 質問への回答や情報の要約を自然な文章で提示できる。 | 利用料金、応答品質、情報の送信先、データ保持、利用条件などがサービスごとに異なる。モデルや提供形態は要検討。 |
| PDFテキスト抽出 | PDFから本文やページ情報を取り出す処理。 | 既存資料を検索対象にするための基本的な処理となる。 | PDFの構造や品質により抽出結果が異なる。表、段組み、文字化け、画像PDFへの対応とページ番号の保持が課題となる。 |

PDF抽出ライブラリ、埋め込みモデル、ベクトル検索方式、LLMの提供サービス、画面/APIの構成は要検討です。選定時には、精度、費用、運用の容易さ、データの取り扱い、利用条件を比較します。

## 11. 今後検討が必要な事項

1. **資料の範囲と管理**：対象とする公開機関・資料、資料の取得・登録方法、更新頻度、利用条件の確認方法。
2. **PDF処理**：表や段組みへの対応、OCRの要否、抽出失敗時の扱い、ページ番号の正確な保持方法。
3. **検索品質**：キーワード検索とベクトル検索の組み合わせ、検索対象件数、チャンクの大きさ、検索結果の評価方法。
4. **回答の仕様**：回答の長さや形式、根拠が見つからない場合の応答、引用の表記、誤回答の評価方法。
5. **技術選定**：LLM・埋め込みモデルの提供形態、費用、データ送信・保存条件、PostgreSQLとpgvectorの適合性。
6. **利用画面と運用**：画面/APIの方式、ユーザー認証の要否、資料登録・更新・削除の担当者と手順。
7. **非機能の目標値**：応答時間、同時利用者数、対象資料数、稼働時間、バックアップ、ログ保存期間。
8. **評価と受け入れ条件**：代表的な質問セット、回答と根拠の正しさを評価する方法、各フェーズの完了条件。
9. **将来機能の範囲**：資料比較や年度差分の見せ方、経営課題・業界動向の対象領域、情報の更新・鮮度の扱い。
10. **利用上の注意**：回答を経営判断に利用する際の確認手順、免責・注意書き、専門家への確認が必要なケース。
